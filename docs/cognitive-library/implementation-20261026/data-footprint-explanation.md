# 原始提交体积拆解与数量级

本页解释上一轮合成资源探针，不修改实际采集、计分或保存策略。77–136KiB和386–679KiB均为一次完整测评的未压缩JSON请求数据量，非报告文件大小、录像或数据库最终占用。

体验版9正式试次，文献对照版45正式试次；两版记录同类字段，正式次数相差5倍。60–120Hz合成场景中，8秒运动每试次约481–961个软件帧时间戳。

## 为什么帧日志大

motionFrameTimesMs逐项用JSON数字表示软件帧回调时间，包含大量小数；它用于保留实际帧间隔、卡顿与时序证据。不同试次都有自己的帧列表，逐帧时间戳占本组合成场景约76%–86%。

纯几何轨迹可按冻结seed/算法/参数重建，但真实帧时间和中断不能靠seed伪造。因此不能直接删除这部分日志而声称保留了相同的研究/重放证据。

剔除帧字段后，体验版约18.4KiB、长版约92.0KiB，只用于解释占比，不代表该删减方案已被采纳或通过验证。

## 数量级

- 600KB（十进制）×1000=600MB=0.6GB。
- 600KiB×1000约586MiB=0.572GiB。
- 600KB×100万约600GB，长期增长确实需要预算和保存策略。
- 加密/base64、存储压缩开关、结果/索引、WAL及备份/副本会改变实际占用，不能把JSON请求字节直接当落库容量。
- 1000份累计保存与1000人集中交卷是不同问题；后者还涉及带宽、解析、加密、DB写入和背压。

## 后续优化边界

这仍是完整帧日志的开发候选，尚未成为上线存储规范。上线前应分清核心原始作答、设备/显示/校准、必要质控证据与完整研究日志，再按重放需求优化编码/无损压缩、重复真值及归档/保留策略。两版的计分与质控口径必须一致；任何减少原始证据的决定显式登记，不静默丢弃数据。

当前平台支持条件式压缩加密，但未核本任务未来部署开关/实际占用，不承诺压缩比或已节约容量。需在保持同一原始证据的前提下，分别测传输、落库和备份。

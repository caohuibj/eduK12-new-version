状态：**待独立审阅、待用户明确批准；未实现，不授权正式施测。** 这是内容开发提案，不是科学准入结论或运行配置。

当前7例的软件路径已由保存数字证明：第三个间隔49.9ms尚不足名义50ms，继续画第4次刺激，下帧约16.7ms后才画mask，得到约66.6ms。保存间隔约16.6–16.7ms，不支持将这7例解释为主线程卡顿。至于时间戳为何落在49.9、API计时分辨率/量化或调度等因素，不能仅凭这些日志作独立归因。

## 建议的保守路线

先在明确的设置阶段观测rAF节奏，冻结此次选择；观察到的rAF节奏不等于硬件面板刷新率。建议初期仅评估60/120Hz两档分别3/6个刺激绘制机会，其后的回调绘制mask。按绘制序号切换，而非每回调用elapsed>=50触发。**实际分类频带、采样长度、稳定性/缺帧规则和准入容差均未定，null不等于通过；这些条件未批准前不能正式开始。**

| 理想rAF节奏 | 50ms对应机会数 | 本提案初期路线 |
| --- | --- | --- |
| 60Hz | 3 | 待审的三次刺激绘制机会 |
| 120Hz | 6 | 待审的六次刺激绘制机会 |
| 90Hz | 4.5 | 建议开始前阻止，不自动选4/5次或交替 |
| 144Hz | 7.2 | 建议开始前阻止，不自动选7/8次 |
| 100Hz | 5 | 数学可整除，但不在初期60/120白名单，仍需单独审阅 |

“3/60=50ms”只是理想数学关系，不证明真实设备或物理像素50ms。真实59.94/120近似节奏、VRR、低电量/后台调度、API时间戳精度等都需数值准入与实机证据；这里不填写一个方便通过的数值。

## 首个真实draw与on/off分别记录

拟将“首个真实draw”严格限定为：该刺激canvas命令组确实发出并无异常返回，随后才提交此draw序号。这仍不是实际屏幕像素onset。分别保存rAF回调参数、进入回调时performance.now、draw命令开始/返回performance.now；刺激首组和mask首组各一套，不能把mask回调参数和刺激绘制结束当作同一种时间。实际屏幕像素on/off未知保持null。

当前capture在记录stage后再由Task绘制；若未来改为记录draw结果才提交counter，属于原始合同/呈现语义变化，必须重新审版本/冻结兼容，不沿用旧字段意义。始终只使用同一timeOrigin/pageInstance；换realm结束该次序列，不跨刷新拼接时钟。

## 确定性边界样例

完整JSON是描述性合同，不是可执行质量规则或新测试通过记录。

- 理想60Hz：stimulus在序号0/1/2，序号3首次mask；理想120Hz对应0–5刺激、6首次mask。
- 复用已见的[0,16.6,33.3,49.9,66.6]序列：旧elapsed路线在66.6才mask；拟三机会路线会在49.9画mask。49.9并不等于50，这证明新路线是实质呈现政策改变，不能把它当作加epsilon的普通修bug。
- 单纯计数也不足：若回调从16.6跳到50.0，继续凑刺激回调次数可能再延长。需在下一组刺激命令前执行获批的缺帧/中断显示策略，保留raw并结束序列；确切检测数值与如何中和画面待审，不能悄悄新增刺激行为。
- 首次绘制抛错、重复/倒退rAF、origin改变，不补造成功onset或推进counter。原始尝试/错误保留，不输出个体解释。

# V2 单行终稿：基线、优化与同快照对照

日期：2026-11-25。基线为 main `9b00c20d0f26fde0b3727b4ad2b46cad9411e424`。实现位于 `perf/whole-v2-final-short-transaction`，当前为本地工作区改动；没有推送、CI 激活、合并或部署。

## 结论与适用范围

原分析的优化顺序合理。主干代码确实在持锁事务中计分、构造模板及编码终稿；普通 FINAL 的事务模板仓库也确实没有接入已提交共享缓存。消除重复模板编码/插入后，再把冻结题本与本次答案决定的计算移到写事务之前，可以减少 CPU、SQL 和事务占用。

必须保留三个区别：Nginx 的 upstream 时间仍包含上游连接、传输和应用排队，不能精确等同计分或数据库时间；把同步计算移出事务并没有使它脱离 Node 主线程；Teacher 每份交卷更新的是 **Run execution 与 assignment**，并非把整个 Run 设置为完成。

本轮测试使用合成的 303 题、9 个量表（8×34+31），走真实共享 V2 HTTP 提交路由、真实 PostgreSQL 16.15 及真实终稿编码/恢复。入口适配器和 Teacher 权威模型是合成的，Teacher 模型包含 organization → Run → execution → assignment 的锁及真实完成状态更新。它不包含真实产品的登录、完整授权、START 或首次开卷 GET，不能与生产日志中的两端绝对延迟直接比较，也没有实现 Teacher 首次开卷减少 GET 的前端改动。

**严格 4C4G 验收尚未完成。** 当前环境的 `cpu.max=400000 100000` 确认有 4 核配额。Docker 虽接受 `--memory=4g`，但 rootless daemon 报告无 cgroups，容器内实际 `memory.max=17179869184`，即 16GiB。没有把该配置误记为有效 4GB 硬限额。压测客户端在服务容器外，但同样共享宿主的 4 核配额。后续编译/测试的全环境内存峰值不作为应用压测内存峰值。

## 变更

- 所有事务模板仓库都能读取已提交的有界共享缓存。冷缓存先按哈希批量查库，仅对真正缺失的模板压缩、加密并插入；新模板仍在对应事务提交后才能推广为全局存在性证明。START 原 API 保留为同一提交包装器的别名。冷查前已哈希的字节被保留，防止异步查询期间原始对象变化使哈希与密文不符。
- 仅对已登录、IN_PROGRESS、冻结且全为量表的仅回执请求提前计算。Flow、表单、Cognitive/SJT、种子/锁定状态、动态引用选择及其他不满足条件的路径保留事务内计算。受控治理回执仍在事务中生成。
- 提前计算留在原提交准入中，在取得**写事务**连接前完成。短事务继续执行幂等/冲突判断、实时权威检查和原锁序，重新核对 epoch、发布版本、作答人、主体、归属、计时策略等，再原子写入一行 FINAL 和完成状态。历史重放优先级及“收到成功回执意味着事务已提交”保持不变。
- 复用现有技术时间线，补齐 V2 URL 匹配，并增加准入、准备、计分/打包模板、事实/原始答案编码、zstd、SQL、连接获取/BEGIN、事务回调与 COMMIT 分段。没有改变 zstd 等级、加密格式或持久化结构。

共享模板命中仍需要为新构造的片段计算内容哈希；本轮没有宣称消除全部序列化/哈希，也没有在发布时预生成所有结果模板。

## 同一快照的性能结果

每个版本两轮，每轮两组各 200 个同时提交的全新作答，无重试。四份主要记录复用完全相同的参与者、题本、答案和数据库快照；每组先有 4 份新作答预热共享模板。连接池/准入均为 16，准入队列 300、等待上限 30s；一个 Node 24.22.1 应用进程，PostgreSQL shared_buffers=256MB。运行 TS/tsx 源码，没有生产镜像构建资格声明。观测时间线在这些轮次关闭。

下表分位数来自两轮各 200 VU 的 400 条回执合并统计，**不是 400 并发**。

| 提交核心 | main P50 / P95 | 最终优化 P50 / P95 | P50 / P95 下降 |
|---|---:|---:|---:|
| Training 合成入口 | 1470.6 / 2453.8 ms | 1448.3 / 2135.9 ms | 1.5% / 13.0% |
| Teacher 合成状态模型 | 1280.2 / 2063.2 ms | 1049.4 / 1739.0 ms | 18.0% / 15.7% |

每轮均为两组各 **200/200** 成功。Training P50 的变化很小，落在本地轮次波动范围内，尚不能声称已经稳定改善；P95 和 Teacher 的改善更清楚。保留较早优化检查点的诊断记录，但没有以中间版本更快的结果替代最终版本。

稳态每份提交 SQL：Training **6→4**；Teacher **12→10**。此计数来自 Prisma 的实际 raw 调用，不包含登录和完整入口授权。所有主要轮次的 FINAL 行占用 P50/P95/max 均为 **5376/5408/5416 bytes**，共享模板数量一致。采样到的应用 RSS 约 0.53–0.60GiB，不能据此补造全栈 4GB 硬限额通过证明。

## 正确性与验证

每轮实际生成 410 条 FINAL（400 份测量、8 份预热及2份重复提交的首次落库），全部恢复出 303 个原始答案和 9 个量表单元。并发同载荷为一份新回执加一份重放，冲突载荷返回 409。

独立原生验证从 410 条终稿完整恢复 **3690 个量表结果**，按同一冻结定义重新计分并逐份比较完整结果哈希；原始答案也与请求逐项相同。故意在 FINAL 写入后回滚、在准备后撤销 Teacher assignment，以及事务模板回滚，均没有留下半完成父记录、execution/assignment 或全局未提交缓存证明。`assessments`、`composite_form_answers`、`assessment_unit_snapshots`、`assessment_result_facts` 和 `composite_report_jobs` 均为 0。

类型检查、受影响单测、原生 START→FINAL/变体/模板约束检查见同目录日志。首次原生回归保留了冷缓存夹具失败：一次性屏蔽全局缓存不足以强制冷查，现改为在该检查期间持续屏蔽，仍要求一次真实 PostgreSQL 读取；没有减弱断言。最后冷查字节快照保护只复验其相关输入，不重放未变化的检查。

## 观测的实际限制

`diagnostic-timeline.jsonl.gz` 有 414 条有效时间线且没有丢事件。该轮另行启用了现有 canonical 调用栈诊断，明显增加了请求开销，因此不混入上表。事务回调/提交的墙钟分段仍包括事件循环调度，不能直接当作纯 SQL、锁或磁盘等待。此观测足以验证分段接入，尚不足以把生产毫秒精确分摊到各资源。没有依据这轮诊断降低 zstd 等级或引入后台线程。

## 复现和原件

- `summary.json`：逐轮与合并统计；`latency.csv`：1600 条主要测量。
- 四个 `*.json.gz`：对应原始 HTTP 回执和全部断言结果；`inputs.json`：精确 base、最终源码/工具、夹具及数据库快照哈希。
- `benchmark-whole-v2-final.ts`、`benchmark-whole-v2-client.mjs`、`verify-whole-v2-benchmark.ts` 位于 `server-version/backend/scripts/`。前者准备合成夹具并启动共享路由；客户端测量两组 200 并发并检查恢复/重放；最后一个在显式 loopback `whole_v2_final_test` 数据库中验证完整结果与回滚。
- 实际使用的应用进程启动脚本 `start-server.sh` 和快照对照脚本 `run-pair.sh` 保存在本机 `/workspace/scratch/whole-v2-final-20261125/`。该目录还保留完整合成夹具和数据库快照；没有把数据库转储或依赖目录加入仓库。本轮临时容器和 main 对照 worktree 已清理。再次测试须重新建立独立 PostgreSQL/Redis 与 main checkout，使用同一快照和参数，并核验容器内有效 cgroup 值。严格 4GB 对照须使用真正支持内存 cgroup 的隔离环境。

本机执行证据不等同正式 CI、生产容量或部署资格。

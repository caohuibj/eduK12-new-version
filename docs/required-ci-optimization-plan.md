# 必跑 CI 提速实施方案

## 目标与边界

在 PR 158 的内容分流之外，缩短必须完整验收的提交从触发到结果齐全的时间。
保留后端真实数据库回归、前端类型检查、浏览器安全边界、Docker、CodeQL 和
fail-closed 合并检查。不得通过跳过失败、放宽业务性能阈值或减少覆盖率来提速。

本 PR 是第一阶段的可试运行实现，默认仍使用现有执行器；尚未启用托管运行，
也没有实测加速比例。PR 158 尚未合并，因此本 PR 以它的分支为基线；先合并
158，再核对本 PR 的差异并改为 main。不要绕过 158 的 CI 合并本 PR。

相差很大，与资源争用的观察一致，但不能据此承诺迁移后会快多少倍。

## 分阶段实施

| 阶段 | 实施内容 | 预计工程量 | 验收与回退 |
| --- | --- | --- | --- |
| 1，本 PR | 三个独立浏览器工作流支持隔离托管执行器；依赖下载和浏览器缓存；35分钟任务上限；耗时统计工具 | 已实现，待试运行 | 相同提交全部验收成功；开关关闭即回到现有执行器 |
| 2 | 将 frontend/backend build 做成当前运行内的公共生产者；主浏览器和三个专用验收下载同一产物 | 1–2个工作日，估算 | 每个产物有提交SHA、平台、Node版本、锁文件标识；生产者失败则消费者失败；回退为原独立构建 |
| 3 | 分析后端耗时分布，先拆无数据库测试与数据库测试，必要时按耗时均衡为2–3片 | 2–3个工作日，估算 | 每片独立PostgreSQL/Redis、迁移和种子；总测试清单一致、关键套件零跳过；回退串行全量 |

阶段 1 优先移走三个竞争者，释放现有 Mac 给主链路，不增加同一主机的 runner
进程数量。不要在同一个数据库和端口上并发运行多个验收。

阶段 2 需先统一工作流编排：优先 reusable workflow + needs 的同一运行产物传递，
不用“最近成功产物”跨提交复用，也不采用不受信任 PR 的 workflow_run 特权执行。
前后端编译产物可复用；node_modules、数据库状态和种子不能跨平台或验收共享。
浏览器消费者仍单独启动服务和加载各自夹具。第二阶段是后续 PR，不在本次暗中重构。

阶段 3 不按文件数平均分片。先收集各文件的实际耗时和共享状态依赖；保留
10/30/60并发 FINAL、200条聚合完成等现有负载与断言。合并报告必须核对预期
测试文件全集、零重复、零遗漏、关键套件未跳过；任何分片失败或取消均阻止合并。
CodeQL 与前端没有数据依赖时可以在独立容量上并行，但不能仅移除 needs 后
让两个重任务争抢同一台 Windows 主机。Docker 层缓存另行按构建耗时收益评估。

## 本 PR 的试运行与配置

三个工作流各增加 boolean 输入 `hosted_runner`，默认 false。
手动运行时选 true，只影响这一次运行。托管系统固定 `ubuntu-24.04`，并继续由
锁文件指定的 Playwright 安装 Chromium 和系统依赖。每个任务有独立临时服务。

建议先选同一提交的一个工作流试跑；通过后再跑其余两个。示例（由维护者执行，
本 PR 未自动触发付费托管试运行）：

```sh
gh workflow run media-7-cross-runtime-acceptance.yml --repo caohuibj/eduK12-new-version --ref ci/required-gate-throughput -f hosted_runner=true
```

待试运行验证后，设置仓库 Actions variable `CI_BROWSER_HOSTED=true`，让后续 PR
的三个专用验收使用托管执行器。删除变量或设为 false 后，新运行恢复 self-hosted；
已经开始的任务不会迁移。如需完全恢复旧配置，可以回退本 PR。

缓存仅保存 `~/.npm` 下载和 `~/.cache/ms-playwright` 浏览器，键包含 OS、架构和
锁文件。npm 仍执行 npm ci；Chromium install 仍执行；Linux 系统依赖不缓存。
self-hosted 保持原本地缓存，避免额外远程缓存传输。未缓存构建输出、访问凭据、
数据库或 node_modules。

这是私有仓库。托管执行器会使用账户配额/计费分钟；本 PR 不改账户预算或日常
开关。三项各35分钟意味着单次尝试最多约105任务分钟（不含缓存存储等费用），
不等于实际账单。启用前由仓库维护者查看现有配额、价格和预算；配额不足可能
导致排队，不能把托管视为无限容量。也可另行配置独立的自托管机器达到队列隔离。

## 衡量方式与上线门槛

1. 记录触发、任务开始、结束、各步骤耗时、结果、测试数、重试次数和缓存命中。
   同时报告墙钟时间和任务分钟总和：并行缩短等待，不一定降低成本。
2. 同一 SHA 先完成三个工作流的托管兼容验证；之后采集至少10组相近范围的完整
   成功运行，区分冷缓存与暖缓存，报告中位数及 P95，不混入取消/失败运行。
3. 初始目标（待验证）：三个验收不再占用主后端执行器；完整验收墙钟中位数下降
   30%以上、开始前等待中位数下降60%以上。任一业务断言退化、重复性失败或
   成本超出维护者预算均暂停扩大使用。十组的P95仅作早期指标，持续积累样本。
4. 第一阶段试运行成功后才开日常开关；第二、三阶段各用独立 PR 和相同口径评估。
   对 main 完整主链路的收益必须在158和本PR均合并并实际运行后确认。

复现统计（需 gh、jq、Node；Jobs API 分页取全）：

```sh
repo=caohuibj/eduK12-new-version
run_id=35707705376
gh api "repos/$repo/actions/runs/$run_id" > /tmp/ci-run.json
gh api --paginate --slurp "repos/$repo/actions/runs/$run_id/jobs?per_page=100" > /tmp/ci-jobs.json
jq --slurpfile pages /tmp/ci-jobs.json '. + {jobs: [$pages[0][].jobs[]]}' /tmp/ci-run.json > /tmp/ci-timing-input.json
node .github/scripts/ci-timing-report.mjs /tmp/ci-timing-input.json
```

统计工具显式区分 dispatch-to-start 与执行时间；未完成、跳过或反向时间戳
不被算作“快速成功”。可用 `node --test .github/scripts/ci-timing-report.test.mjs` 验证。

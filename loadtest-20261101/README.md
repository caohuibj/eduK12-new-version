\* R1 p95 为首请求建连离散（小样本）。

**关键结论：**
1. **服务端零退化**：R150/R200 饱和窗口内，Nginx trace 全命中（17,141/12,272），100% 返回 200，服务端 rt p50 仍 9–10ms、p99 <75ms——客户端测到的延迟膨胀与 59 个连接级失败 **100% 是发压源 3Mbps 带宽饱和**（VU 翻倍而送达 RPS 不升反降：273.7→244.1 = 源瓶颈铁证）。
2. 读路径在可测范围内（~270 RPS 喂入速率）容量余量极大；峰值期 backend CPU ~32%（单核）、postgres ~27%、DB 连接仅 +3（26 idle + 1 active）。
3. 认证读全程**零写入**（前后 DB 快照逐字节一致：471MB、WAL LSN 不动、pg_stat_wal 零增长）。
4. 3Mbps 发压源在 ~170–240 RPS 区间饱和；**更高读容量无法从该源测得**，不是生产上限。

## 四、写矩阵（作答→报告全链路并发）

设计：每（学生，问卷）对 1 次合法 attempt；问卷 6cd8a15a（max_attempts=1/人）；
并发 W1→W5→W25。每次提交使用独立 submissionId（ltwm-<uuid4>）、模板绑定当次 definition 冻结字段、FINAL 仅一次、报告 25 项分数逐一验证。

| 阶段 | 并发 | 完成 | FINAL ACK | FINAL→验证报告 |
|---|---|---|---|---|
| W1 | 1 | 1/1 | 94.6ms | 1,230ms |
| W5 | 5 | 4/5 | 68–76ms | 1,177–1,205ms |
| W25 | 25 | 24/25 | 65–477ms（中位 ~90） | 592–2,455ms（中位 ~1,250ms） |

- W25 墙钟 **16.1s 完成 24 条完整作答+报告生成**（25 路并发）；burst 下个别 ACK 391–477ms、报告等待 ~2.3–2.5s，无失败无重放。
- 2 条失败记录（均无服务端副作用，DB 验证）：W5 record-1 为跨阶段学生复用碰撞（预期语义失败）；W25 record-20 为 START 前 ReadTimeout（**无孤儿 attempt**，该生额度未消耗）。
- 写容量代价（29 条完整作答+29 份报告）：表数据 +2MB、WAL +4.2MB ≈ **每份 ~70KB 数据 + ~145KB WAL**。
- 报告 job：29/29 完成；服务端 acceptedAt→completedAt 基线 154–630ms（均值 ~390ms）。

## 五、发现与优化记录（未改动生产）

1. **两 API 副本负载极不均**（R50 峰值实测 backend 31.7% CPU vs backend-2 0.20%）：疑似 upstream keepalive/权重导致流量集中单副本。建议排查 `docker-compose.prod-override.yml` upstream 配置；修正走仓库下版本。
2. **报告状态轮询可提速**：服务端 retryAfterSeconds=0.1，诊断客户端保守等待 1s，端到端多 ~0.9s；真实客户端应遵循服务端建议（注意 25 次/120s 上限）。
3. **登录可观测性**：登录逐请求耗时此前无处可查（auth-events.json 未随会话归档、Nginx timing.log 无时间戳/路径、backend 无 auth 日志）。建议：会话交接 SOP 附带 auth-events.json；Nginx timing 格式加 `$msec`/`$request`（下版本）。
4. **压测问卷池不可直接作写目标**：池问卷（course_id 为空）START 409；两个 max_attempts=50 问卷中 63a1f5c4 定义端点 409（未完整供给），d8e6070c 为 3 单元不同构。有效写通道 = 测试问卷 × 新学生（每人 1 次）。本轮遗留 1 个 IN_PROGRESS attempt（63a1f5c4，attempt 8839f0b4，学生 d2966000…），无需处理但记录在案。
5. **pg_wal 保留 1025MB**（默认上限附近）：4 周运行+当日迁移后正常；磁盘紧张再议 checkpoint 调优。
6. attempts/report_jobs/answers 均为 7 分区表；pg_stat_activity 峰值 27 连接（池健康）。

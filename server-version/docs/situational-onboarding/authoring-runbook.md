# SJT content authoring and publication

Run commands from `server-version/backend`.

1. `npm run situational:scaffold -- my-new-sjt@1.0.0 --from sjt-assertiveness-golden@1.0.0` creates a copy to edit, explicitly DRAFT/PILOT. It never copies publication approval and refuses to overwrite an identity.
2. Edit `instruments/<key>/<version>/instrument.json`: the existing V1 or V2 definition and independent golden expectations. Edit all task wording/rights/interpretations for the intended instrument. No JS/TS, scorer upload or new frontend runner is accepted as ordinary content.
3. `npm run situational:manifest:generate` and `npm run situational:onboarding-check -- --all --json`. Schema errors, duplicate identities and manifest drift are build errors. Structurally valid incomplete DRAFTs report technical blockers without becoming participant-admissible.
4. Use `--content-only --base <full-base-SHA>` to verify the actual tracked and untracked diff. Only owned JSON/test data/assets and exactly regenerated manifest are allowed. Generator, CI, policy or shared code changes are platform work.
5. Open a DRAFT content PR and obtain a human GitHub APPROVED review from an independent collaborator with write/maintain/admin permission. Approval must cover the exact content digest printed by the gate. Copy its real `https://github.com/caohuibj/eduK12-new-version/pull/<n>#pullrequestreview-<id>` URL into publication.json, with `kind: github-review` and `contentDigest`, then explicitly set releaseStatus to PUBLISHED. Do not invent review records.
6. CI validates the review state, independence, repository permission, superseding review and content at the reviewed commit. Changing content invalidates the receipt. Merely passing a technical gate does not publish anything.
7. Before deployment, complete the required backend/frontend/browser gate and content review. Media references use the existing immutable StoredAsset identity/contentHash; actual deployment asset readiness and bytes are checked by the existing asset service/browser lane. Offline schema checks cannot certify a remote asset exists. No new media store is introduced.

Once published, changing instrument.json requires a new instrumentVersion (including changed golden expectations/catalog presentation). A changed scoring contract also needs an appropriate scoringVersion. Exact old identities are retained. DRAFT -> PUBLISHED -> RETIRED affects admission, not definition/runtime hashes. Retirement preserves frozen completion/history and does not require reapproving the original author’s scientific claims.

`scientific.json` owns scientific declarations independently of execution/publication. Follow [scientific review workflow](scientific-review-runbook.md) for scoped evidence, verified human approval, revisions and withdrawal.

## CI activation / human decision boundary

The main ruleset requires `merge gate / ready PR`. PR2 retriggers that required full workflow on review submission/dismissal, so the authority check participates in the enforced gate after review changes. The independent `publication` check remains an additional signal. No repository-wide ruleset change is required by this implementation.

## Staff-uploaded Excel / JSON templates (sjt-upload-v1)

This platform extension is developed locally on the vnext branch, with no push, PR, remote CI, production content import, or deployment. Integrate with the preceding main work after it merges, as one reviewed platform PR. The existing code-owned publication and scientific review gates above still apply to the code-owned registry. Staff uploads use a separate audited database release store; an administrative upload review never substitutes for scientific validation.

Teachers and administrators use `/sjt-authoring`. Download the blank or filled workbook, check it, save a private draft, preview all stages and the report, then request an independent administrator's review. Authors cannot approve their own draft, even if they are administrators. The review binds the exact revision and content digest. New revisions or restores invalidate a pending review. Restoring creates a new revision; published versions cannot be overwritten. A new content version needs a new draft. Administrators can retire releases, stopping new admission while frozen in-progress and completed attempts retain their original execution and report.

The workbook contains basic metadata, nodes, questions, options, transitions, metrics, scoring opportunities, contributions, narrative fragments, repeated-question comparisons, and independent acceptance responses/expectations. Every node × metric must explicitly be OPPORTUNITY or NA. Every valid core option needs a transition and every applicable contribution, including zero; NA and nonanswers have no contribution. Optional text is bounded, unscored, excluded from participant narrative and current research export. The server accepts declarative data only: no uploaded scripts, formulas, macros, external links, or embedded objects. File size, actual decompression, XML, rows, columns, graph, references and report rules are checked before release. Errors identify the worksheet and cell/row for field errors; graph and collection failures identify their source table and reference.

The compiler creates V2 branching definitions, expanding only incoming bridge text while retaining logical-node/mother-scene identity and convergence. Each core action must be confirmed before post-action probes appear. Probes are optional RAW_ONLY. AUTHOR_KEY_SUM@1 sums provisional author contributions; EXPERT_KEY@1 retains its existing mean rule. U/N remain explicit nonanswers, never zero. Missing applicable contributions produce null metrics. Ordinal comparisons require the same mother scene, prompt and five category anchors; their movement is descriptive, not interval measurement or causal/ability change. The participant receives matched narrative only after the full trajectory finishes, with one final reminder per mother scene. Full report rules and contribution keys stay server-side. Participant JSON/CSV exports contain the narrative and frozen scope, not the provisional numeric score display.

Administrative releases remain PILOT with a frozen scope documenting the absence of scientific calibration. No norms, latent trait estimates, production research grants or new anonymous research authority are introduced. Teacher participation has a separate `/api/teacher/situational` surface restricted to teacher-targeted releases. Existing student routes and exact-resource research authorization retain their boundary. The first upload format is for standalone text delivery; whole-attempt experiment arm/order randomization, a retrospective phase, multimedia upload, and anonymous research admission remain future extensions.

The filled workbook adapts the two 2026-10-01 mother scenes, six logical nodes and 18 questions, with the author's 128 independently calculated core paths and six additional U cases. Its U/N neutral bridges and nonanswer prose are platform adaptations that require author confirmation before real use. It is downloadable example content, not a production-published registry entry. Publication requires independent expected metrics and coverage of every configured core and probe option, including U/N.

Local verification: `src/__tests__/situational/sjt-authoring.test.ts` covers independent scoring paths, old-model compatibility, freezing, nonanswers, optional text privacy, malformed definitions and workbooks, executable cells, external links and actual decompression limits. The opt-in `sjt-authoring.postgres.integration.test.ts` requires `SJT_UPLOAD_INTEGRATION_DATABASE_URL` pointing to the dedicated synthetic PostgreSQL port 55473; it covers ownership, independent review, revision CAS/restore, immutable versions, retirement, and concurrent FINAL replay. `e2e/sjt-upload-browser-acceptance.cjs` uses synthetic staff sessions, an isolated local database and real Chromium to cover the upload/review/teacher journey and denied research access. Never point these fixtures at a developer or production dataset.
